New to Temporal?

Start with a job that can survive a restart.

Imagine an application that asks a model to generate a detailed climate map, checks the result and writes a report. The model call can take time. If the program managing the job stops, the application still needs to know which steps finished and what to do next.

Temporal is a platform for coordinating that kind of job. Its service records a job's progress and makes tasks available to application programs called Workers. A Worker runs the application code. If a Worker disappears, another available Worker can use the recorded history to continue the job.

A Workflow is the plan.

Workflow code decides the order of steps and how to respond to their results. In this guide, it schedules inference and then reporting.

An Activity does the work.

An Activity performs work outside the Workflow's decisions. Here, Infer calls the model service, and Report prepares the explanation.

Event History is the record.

The Temporal Service records events, including completed Activity results. Workflow code can use that history to reconstruct its progress.

For example, Infer can finish and Temporal can record its result. If the Worker then stops, another Worker can reconstruct the Workflow and continue toward Report. The recorded result supplies the completed inference step.

Retry and replay answer different questions. A retry starts another Activity attempt after a failure. Replay runs Workflow code against saved history to reconstruct its decisions or check compatibility. Replay can use a recorded Activity result without calling that Activity again.

A retry may repeat external work. Temporal does not automatically stop a separate model service or save the model's partial computation.

This introduction is a conceptual example. The failure explorer shows the recorded research results. The execution chapter explains the mechanisms in more detail. The glossary defines the terms used throughout the guide.

Start with the idea

The saved decision and the running computation are different things.

A sampler turns noise into a generated field through repeated model calls. PC-RF uses this idea for climate downscaling. A single request can perform enough work that restarting it matters.

Temporal saves a job's decisions and results so its orchestration can continue after a Worker fails. The model computation runs in a separate Rust service. Saving the job's progress does not automatically cancel that service or checkpoint its sampler.

The key question is what happens when the caller disappears while the computation is still running. This research build makes that failure visible and measures the next attempt.

The technical guide

Temporal records decisions while Workers run code

Durable Execution lets a job continue from recorded progress after a process fails. Temporal provides the saved Event History and task scheduling. A Worker runs the application code. The Rust inference service remains a separate process with its own computation and lifetime.

The request crosses explicit ownership boundaries

The Go gateway accepts a request and starts a Workflow. A Workflow describes the order of application steps. Here it schedules Infer, waits for its result and then schedules Report. An Activity performs work outside the Workflow's deterministic decisions, such as a network request. Infer calls the Rust service through gRPC. Report requests explanatory text through HTTP and can return a fixed template.

The Temporal Service records events and schedules tasks on a Task Queue. Workers poll that named queue and run the corresponding Workflow or Activity code. The same Worker process in this build runs both kinds of code. The Temporal Service does not execute the neural network. The Rust service receives the RPC and performs the sampling work.

Recorded results let orchestration continue

An Event History is the saved sequence of events for a Workflow Execution. It records decisions and outcomes needed to reconstruct the Workflow's progress. When Workflow code runs again against that history, completed Activity results can be supplied from the record. The Workflow can then determine what should happen next without repeating a completed model call merely to reconstruct its state.

A conceptual example starts after Infer has completed and its result has been recorded. A Worker can disappear before the reporting step finishes. Reconstructing the Workflow uses the recorded inference result to reach the reporting decision. This explanation concerns saved orchestration progress. It does not imply that a sampler interrupted before completion has a usable checkpoint.

An Activity attempt and a sampler run are different

An Activity attempt is an attempt to execute Infer. It might fail while connecting, before any sampling begins. It might also start a sampler that continues after the calling Worker disappears. Counting Activity attempts alone therefore cannot establish how often the model actually ran. The experiment checked the attempt field in the saved events and separately counted sampler completions.

The Rust service starts sampling in a blocking task. That task continues after the RPC client disconnects in this implementation. Killing the Worker ends its ability to report an Activity result, but it does not automatically terminate the computation already running in Rust. A replacement Worker can consequently ask the service to run the same request again. Durable orchestration and computational cancellation require separate designs.

The experiment measures a local request path

This is a research system, not a commercial production deployment. Every campaign measurement used one Apple M4 Pro laptop CPU, a demo-scale model and five runs per scenario. The Temporal dev server stored Event History in a local database file. A single request went through the gateway, while the campaign started Workflows through the Temporal CLI. The campaign therefore does not measure gateway throughput.

A future service design would need an explicit policy for repeated external work. An idempotency key lets a service recognize repeated requests and apply an agreed response policy. This build has no Activity idempotency key. A seed selects a random state, but it does not by itself prevent duplicate computation or define how completed results are stored and reused.

The technical guide

The sampler generates a checkable field

PC-RF means Physics-Constrained Rectified Flow. It is a conditional generative model for climate downscaling. This research build uses a small export to study how a long model call behaves when its surrounding services fail. The experiment measures orchestration behavior, and it does not establish climate accuracy.

Downscaling asks for detail under constraints

Downscaling aims to produce a finer spatial field from coarser information. A generative model can produce different possible fine fields for a conditioning input. The conditioning guides generation, while a random seed controls the initial random state. An ensemble collects generated members so the service can form their mean. A plausible-looking map still needs checks that reflect the physical quantity it represents.

The model package includes penalties for wind divergence, negative precipitation and disagreement with coarse precipitation mass. A penalty adds a cost during training when an estimated clean field violates a chosen condition. These mathematical choices express modeling assumptions. They do not establish that every atmospheric process follows the simplified constraints, or that an accepted field matches observed weather.

The Rust service owns the sampling loop

Rectified flow learns a velocity field that moves an evolving noisy state toward a data-like state. The exported ONNX graph evaluates that velocity from the current state, the integration time and the conditioning. The Rust service repeatedly evaluates the graph and updates the state with Euler integration. ONNX Runtime evaluates the neural network, while Rust owns the surrounding loop and the final metric calculations.

The recorded standard request uses 1500 sampler steps and 4 ensemble members. The experiment ran on one Apple M4 Pro laptop CPU with a demo-scale model and five runs per scenario. Its model has a 64 by 64 tile, base width 32, no attention and brief synthetic training. The baseline inference median was 16.130 seconds, with an observed range of 15.740 to 18.054 seconds. The measured Go path forwards no conditioning tensor, so the Rust service uses its synthetic conditioning path. These values describe this particular call and environment.

Projection and acceptance serve different purposes

The optional inference projection changes the precipitation values after sampling. The Rust implementation clamps negative values and rescales the remaining precipitation toward the requested coarse mean when its conditions permit. A later acceptance gate decides whether the returned metrics satisfy the request policy. Projection changes an output. The gate accepts or rejects an output. The implementation keeps those responsibilities separate.

The negative-value rate, NVR, measures the share of precipitation cells below zero. The mass conservation error, MCE, measures relative disagreement between the fine precipitation mean and the requested coarse mean. The default gate requires NVR equal to 0 and MCE below 1e-3. The service also reports divergence error, but that metric does not determine acceptance in this gate.

An ensemble mean can hide member failures

The service computes the reported metrics on the ensemble mean. A conceptual example is an ensemble whose members have errors in different cells. Averaging can reduce those errors even when an individual member remains unacceptable. A passing mean therefore does not establish validity for every member. The physics gate checks the ensemble mean only.

The useful question for this experiment is whether orchestration handles a returned domain failure differently from a lost call. That question does not require treating the small model as a validated climate predictor. A future scientific evaluation would need suitable observations, accuracy measures and member-level checks that address the intended application.

The failure type determines whether another attempt helps

A Retry Policy tells Temporal whether and when to try an Activity again. A useful policy distinguishes a temporary inability to complete a call from an output that violates the application's acceptance rule. This distinction determines both repeated work and how a failure reaches the caller.

The policy bounds attempts and spaces them apart

The Workflow sets Maximum Attempts to 3 for Infer and Report. The recorded Retry Policy has an initial interval of 1 second and a backoff coefficient of 2. Backoff spaces repeated attempts apart after failures. These are the settings of this build, rather than a measured recommendation for every inference service.

Maximum Attempts bounds the attempt count. It does not alone set a deadline for the entire job. Each attempt can spend time running, and a retry can spend time waiting for a Worker. Start-To-Close Timeout limits an attempt after it starts. The experiment chose 2 minutes for that setting and did not vary it. A design with a total latency requirement must also account for waiting and backoff.

The same policy can finish or exhaust its attempts

The brief-outage scenario stopped the inference service and restarted it during the retry window. The last attempt reached the service and completed sampling. On one Apple M4 Pro laptop CPU with the demo-scale model and five runs, the Workflow median was 19.466 seconds after 3 attempts. The first retry start time is UNVERIFIED because the fast failed attempts ended between polling observations.

The service-down-throughout scenario kept the inference service unavailable. On the same Mac CPU with the demo-scale model and five runs, the Workflow failed after 3 attempts with a median of 3.026 seconds. The connections were refused quickly, and the sampler never ran. This result does not establish how quickly retries would end when a remote service accepts a connection but responds slowly.

The physics gate makes failure a domain decision

Infer reads the returned NVR and MCE values and compares them with the request's limits. It also rejects missing metrics, invalid limits, non-finite values and values outside the accepted ranges. A failed check returns a Non-Retryable Error named PhysicsCheckFailed. That error stops Activity retries. The Workflow then returns Infer's error, so this Workflow Execution fails too.

The invalid-output scenario used 20 sampler steps with projection disabled. All five runs on one Apple M4 Pro laptop CPU with the demo-scale model stopped after an attempt, with a median Workflow duration of 0.224 seconds. That duration belongs to the shorter request. It does not measure how quickly a full-length sampler would fail its post-sampling check. The physics gate checks the ensemble mean only.

Seeded metrics support a narrow conclusion

The separate reproducibility check repeated a seed-7 request with 20 sampler steps and projection disabled on the same Mac CPU and demo-scale model. The repeated calls returned matching divergence, negative-value and mass conservation metrics for the ensemble mean. This was a repeated-call check, separate from the five-run scenario groups. Full field identity and reproducibility on other hardware remain UNVERIFIED.

A conceptual policy example is a request that repeatedly violates an unchanged domain rule. The application can stop and ask for a changed request or model configuration. It should make that decision explicitly. The measured matching metrics support this build's choice, but they do not prove that every stochastic model or every domain failure should be marked Non-Retryable.

The technical guide

A Heartbeat Timeout bounds silence from an Activity

A killed Worker cannot report that it has disappeared. Temporal can end a silent Activity attempt through a timeout and then apply its Retry Policy. The experiment asks how that mechanism changes the wait before another attempt, while tracking the sampler work that recovery repeats.

The Heartbeat comes from the RPC wait loop

Infer starts the gRPC call in a goroutine, a concurrent Go function, and waits for either its result, a ticker or cancellation. The ticker calls RecordHeartbeat every 2 seconds. Its payload contains the request seed. The payload contains no partial sample or integration state, so another attempt has no sampler checkpoint to restore.

The Heartbeat shows that the Activity wait loop is alive. It does not show that the Rust sampler is making progress. A slow or stuck sampler could leave that loop recording Heartbeats. The SDK may throttle Heartbeats before sending them, and the experiment did not measure when the Temporal Service received each Heartbeat. The recorded ticker interval is therefore not a measured server-receipt interval.

The comparison changes the timeout setting

Both Worker-killed groups recorded Heartbeats. Their difference was whether Infer had a Heartbeat Timeout of 10 seconds. Both retained the chosen Start-To-Close Timeout of 2 minutes. The test script killed the Worker with SIGKILL, which forcibly stops the process, during Infer and started a replacement. The comparison tests that timeout setting under this failure procedure.

Each group had five runs on one Apple M4 Pro laptop CPU with the demo-scale model. The median failure-to-next-attempt interval was 9.953 seconds with the Heartbeat Timeout and 117.873 seconds without it. These values are consistent with the chosen settings. The interval includes retry backoff, Worker availability and dispatch delay. It does not isolate the Temporal Service's internal timeout detector.

The history supplies a different kind of evidence

The saved start event for the later Activity attempt includes the preceding attempt's failure. Its timeout type identifies a Heartbeat timeout in the enabled group and a Start-To-Close timeout in the disabled group. The failure source is the server. These fields establish which timeout ended the attempt, while the external timing establishes when another attempt began.

The Heartbeat Timeout is measured from the last Heartbeat received by the Temporal Service, not from the later kill command. The Start-To-Close Timeout begins when the attempt starts. Those clocks have different starting points. Subtracting the kill time from the next attempt's start cannot reveal the exact instant at which either timeout was recognized.

Less waiting still leaves repeated computation

Recovery ran the sampler twice in all 15 worker-kill runs across the campaign. Those results came from one Apple M4 Pro laptop CPU with the demo-scale model and five runs per scenario. The original Rust task continued after the Worker disappeared, and the retry started another sampler run. A Heartbeat Timeout saved waiting time in this build and did not save compute.

A conceptual next design would coordinate cancellation or reuse with the inference service. A checkpoint would need usable sampler state and a policy for restoring it. Cancellation would need evidence that the real Rust computation stops. The existing cancellation test used a fake service. Graceful Worker shutdown and cancellation of the real sampler remain future tests.

Replay checks Workflow decisions against saved history

Workflow replay and seeded model reproducibility answer different questions. Replay asks whether Workflow code remains compatible with recorded decisions and results. A repeated seed asks what the model returns when it runs again. This separation matters when code changes while a job is still in progress.

Determinism concerns the recorded command sequence

The Workflow schedules Infer, waits for its recorded outcome and then decides whether to continue to Report. Temporal reconstructs those decisions by running Workflow code against the Event History. Completed Activity results come from the saved record. Replaying a completed inference Activity therefore does not call the sampler merely to reconstruct the Workflow's state.

The relevant contract is compatibility between the Workflow's decisions and the recorded history. A model can produce a stochastic result inside an Activity, and that completed result can still be recorded for replay. Conversely, a model can return matching seeded metrics while an incompatible Workflow code change breaks replay. Model repeatability cannot replace a Workflow compatibility test.

The Replayer exercises a saved execution locally

The Go test creates a Replayer, registers DownscaleWorkflow and passes it a saved Event History. The assertion requires the replay to return no error. This checks the current Workflow code against a specific execution that happened previously. It does not start a new inference campaign or test the current network connection to the model service.

A deliberate scratch edit inserted a timer before Infer. The saved history expected Infer to be scheduled at that point, and replay reported a command mismatch. Removing the edit restored the passing test. The replay test covers one code transition and one saved history. It uses no GetVersion guard, and the experiment did not use Worker Versioning.

Already scheduled work keeps its recorded options

The replacement scenario began with an older Worker build that scheduled Infer without a Heartbeat Timeout. The script killed that Worker and started a newer build that sets the timeout for newly scheduled Infer work. The existing Activity kept its original options. Updating the code did not rewrite the earlier scheduling decision in this experiment.

The replacement group had five runs on one Apple M4 Pro laptop CPU with the demo-scale model. Its median failure-to-next-attempt interval was 117.873 seconds, consistent with the retained 2-minute Start-To-Close Timeout. This interval includes backoff, Worker availability and dispatch delay. The replacement runs test this code transition. The separate replay check uses a single saved history, so neither result establishes compatibility for arbitrary future changes.

A useful fixture represents a real decision path

A conceptual extension would preserve histories from the application's important paths, including successful inference, domain failure and reporting fallback. A replay check can then ask whether a proposed edit remains compatible with those recorded paths. The choice of fixtures determines what the test exercises. Passing a fixture says nothing about an execution path that the fixture never reaches.

The next engineering question is how a particular change affects executions already in progress. New requests may receive newly chosen Activity options while older requests retain earlier decisions. A deployment plan would need to account for both populations and the intended compatibility mechanism. This experiment demonstrates a specific transition and leaves the broader versioning strategy for future work.

The report explains results without deciding their physics

The optional language-model report sits after successful inference. It turns the returned metrics into text. The numerical acceptance decision already happened inside Infer, which keeps a reporting dependency from deciding whether a field passes the physics gate.

Report can use an agent or a fixed template

Report checks whether an agent address is configured. If it is, the Activity sends the metrics to the agent over HTTP and uses the returned report when that call succeeds. If the call returns an error, or no address is configured, Report formats a fixed template containing the field dimensions, backend, inference latency and physics metrics.

The template gives the application a text result when the optional dependency cannot be reached. It does not create new numerical evidence or validate the agent's prose. The numerical metrics remain the basis of the physics decision. The pinned implementation accepts a successfully decoded agent report, and the experiment does not establish whether that text is accurate or useful.

The measured fallback is inside the Activity

The unavailable-agent scenario pointed Report at a verified unused local port. The HTTP connection failed, and Report returned the template. All five runs on one Apple M4 Pro laptop CPU with the demo-scale model completed. Their median Workflow duration was 16.271 seconds. This is a result for an unreachable local agent endpoint, not a general bound on reporting latency.

The Workflow also contains a separate branch that would preserve the inference result if Report returned an error. That branch writes a report-unavailable marker. Report never returns an error in the measured implementation, because its fallback returns a template with no error. Only a mocked test exercised the Workflow's report-unavailable branch. The live fallback and the mocked branch provide different evidence.

An optional dependency can still consume time

An unsuccessful HTTP request must return before Report can select its template. A connection that is refused immediately behaves differently from a request that remains open without a useful response. The measured scenario covers the first behavior. The build did not measure a slow agent or a bad reply, so those cases cannot inherit the successful fallback timing.

A conceptual follow-up would test delayed responses, malformed responses and cancellation through the real reporting path. The application would need an explicit policy for how long explanation may delay a useful inference result. That policy should preserve the accepted metrics and make the reporting state clear. The recorded experiment supplies a starting case, not a complete failure taxonomy.

The evidence supports a focused engineering lesson

The research build separates decisions that are often combined. Retry policy governs repeated attempts. The physics gate decides whether a returned output is accepted. Timeouts allow a silent attempt to end. Replay checks compatibility with saved Workflow decisions. The reporting fallback preserves an explanatory path when an optional local dependency cannot be reached.

Every campaign measurement used one Mac CPU, a demo-scale model, the Temporal dev server and five runs per scenario. Full field identity, other-hardware reproducibility, the brief-outage first retry start, remote CI and container builds remain UNVERIFIED. Real-traffic load, graceful Worker shutdown and real sampler cancellation need further experiments. The educational value lies in linking each mechanism to the exact failure and evidence it addresses.

The terms, in plain language

You can look up the moving parts.

The glossary explains the terms used in this guide.

Temporal

Temporal stores the Event History of a Workflow Execution and schedules work for Workers.

Durable Execution

The application can continue from recorded progress after a process fails. External computations still need their own retry and cancellation policies.

Workflow

Workflow code decides which steps to schedule and how to respond to their outcomes. It runs in a Worker against saved Event History.

Activity

An Activity performs external work, such as calling an inference service. An Activity may have multiple attempts.

Worker

A Worker polls a Task Queue and runs Workflow or Activity code. The Temporal Service and the Rust inference service are separate processes.

Task Queue

A Task Queue is a named destination for work. A Worker polls it to receive tasks it knows how to execute.

Event History

An Event History records the events needed to reconstruct a Workflow Execution, including Activity results and scheduling decisions.

Retry Policy

A Retry Policy controls repeated attempts after a retryable failure. Its attempt limit and waiting intervals have different roles.

Non-Retryable Error

An application can mark a failure as non-retryable when repeating the same Activity request is not the chosen response.

Heartbeat

An Activity records a Heartbeat to report liveness and optionally progress details. This build records a seed, not a sampler checkpoint.

Heartbeat Timeout

This timeout limits silence since the last Heartbeat received by the Temporal Service. It is not a clock that starts at the kill command.

Start-To-Close Timeout

This timeout limits an Activity attempt after it starts. It does not by itself bound the entire Workflow duration.

Replay

Replay runs Workflow code against saved Event History. Completed Activity results can come from that record without executing the Activity again.

Replayer

A Replayer checks whether Workflow code is compatible with a saved history. The research check covers one code transition and one saved history.

Sampler

A sampler repeatedly calls a learned velocity network and updates a noisy state. The Rust service owns this loop in the measured build.

Ensemble

An ensemble contains several generated fields. The reported physics metrics in this build describe their mean.

NVR

The negative-value rate measures the share of precipitation cells below zero. The Activity gate requires NVR equal to 0 by default.

MCE

The mass conservation error measures relative disagreement between the generated precipitation mean and the requested coarse mean. The default limit is 1e-3.

DE

Divergence error is a reported diagnostic. It does not control acceptance in the Activity physics gate.

Idempotency

An idempotency policy defines how repeated requests affect an external service. This build has no Activity idempotency key, and a seed does not prevent repeated work.

ONNX Runtime

ONNX Runtime evaluates the exported neural network graph. It does not own the Temporal Workflow.

gRPC

gRPC is the remote-call protocol used between the Go Infer Activity and the Rust inference service.

The timing definitions matter.

Workflow time runs from the Workflow-start event to its last history event. Infer attempts come from the attempt field on the last Infer start event. The parser does not count start events as attempts.

Sampler counts come from completion records inside the Rust sampling task. Failure-to-next-attempt time runs from the recorded kill or stop command to the next distinct observed Activity start.
